# 踩坑记录与阈值由来

实战(478 文件 7GB 营销文案素材包)总结,供调参和排障。

## 质量判定阈值
- PDF:平均字符/页 ≥80 判 text,≥15 判 sparse,<15 判 image。依据:正常文字版 PDF 每页几百到上千字;扫描版/设计版每页提取出的"字"个位数(还多是噪声)。
- PPTX 用更低阈值(60/12):PPT 每页文字本就比正文 PDF 少。
- 扫描书 OCR 采样阈值 150 字/页:实测扫描文字书(李欣频、Neil French)采样 300-1500 字/页;设计版面(蕉内品牌手册、滴滴视觉方案)采样 10-70 字/页。150 能干净分开。

## 提取层
- `MuPDF error: syntax error...` 是**警告不是错误**,文件照样提取成功。日志里大量这种是正常的,别当失败。
- epub 本质是 zip+xhtml,直接解析,不用 calibre。同书的 mobi 标 skip_duplicate(epub 已含内容)。
- 老格式 .ppt:textutil 读不了(只支持 .doc),python-pptx 也不行。必须 LibreOffice。

## 乱码层
- 现象:某些 PDF 用子集字体,ToUnicode 映射坏,把字编码成康熙部首区字符(⽂⻚⼩,U+2E80–2EFF / U+2F00–2FDF)或重复字形(整理理、不不)。
- 修法两步:① 只对部首区字符做单字符 NFKC 归一化(⽂→文)。**不要对全文 NFKC**,那会把全角中文标点(，。)转成半角,污染文本。② 部首归一化后这些字常和邻居成叠字(文文),再去重——但只去"本文件内反复出现 ≥3 次"的相邻重复字,避开正常叠词(慢慢、渐渐)。乱码字在一篇里重复几十次,正常叠词就一两次,阈值 3 能分开。
- 局部乱码救不干净:有的 PDF 只是某几页字体坏(如某书的悼词页),全文叠字率很低但局部高,脚本去重阈值不触发。这种残留不影响"当土壤用",要彻底干净得 OCR 重提那本。

## OCR 层
- tesseract 中文(chi_sim+chi_tra)对清晰印刷体效果很好(实测错误率 2-3%,如"莺歌"→"营歌")。够当参考土壤,不够精确引用。
- dpi 150 已足够,不用更高(更慢)。
- 中英混排的书,英文部分 chi_sim 会乱(WwWWwW),中文部分 OK,通常可接受。
- 长时间 OCR 后台跑时,Python print 重定向到文件是块缓冲,日志会延迟不更新——别以为卡住了。用输出文件的 size/mtime 旁证进度,或 pgrep tesseract 确认在跑。
- 设计型文案合集(江小白瓶身、奥美电商培训):文案是艺术字嵌设计,OCR 采样字数低会被判跳过。这类要救只能视觉模型逐页读,成本高,挑高价值的做,别全做。

## 删原始的安全红线
- text/sparse 内容已完整进 `_raw` 留档,删原始安全。
- image/failed 内容没进库(在图里/已损坏),删了永久丢失。
- 顺序:verify 通过 → cleanup 预览 → 跟用户讲清图片型会丢 → --apply。
- 实测:典型素材包 89% 体积是文字型大文件(已进库可删),图片型只占约 11% 体积但是唯一"删了会丢内容"的部分。

## 分类
- common.py 的关键词是营销/文案领域配的(文案珍藏/品牌手册/平台运营/行业报告/营销策划+6子类)。换领域改 CATEGORY_RULES/SUBCATEGORY_RULES。
- 兜底类目"其他"和兜底子类"品牌综合方案"会偏大,正常。分类是为检索方便,错几个用户手动挪即可,不必追求完美。

## 增量与兼容(v0.2 重构)
- v0.1 的 extract 重跑会从零重建 manifest,直接抹掉 OCR/转换/修复状态——这是当年"跑一次就不敢再碰"的根因。v0.2 以相对路径 rel 为唯一键增量合并,`is_settled` 的记录(提取物在库、质量态非 failed/unsupported/needs_conversion)默认不动,增量入库=丢新文件+重跑 extract。
- 老库(v0.1 manifest)没有 rel 字段:rec_key 回退用 name;safe_md 对无 rel 的老记录保持旧文件名(不带扩展名后缀),避免升级老库时 431 个文件名整体漂移、外部引用全断。新记录文件名带扩展名后缀(a.pdf.md / a.pptx.md),同名不同格式不再互相覆盖。
- _raw 文件名把相对路径压平(子目录__文件.pdf.txt),压平撞名时追加 10 位 sha256 后缀(bounded_filename 兜底场景取 12 位)。
- OCR 逐本落盘 manifest:28 本书全本 OCR 是小时级任务,v0.1 中断全丢重来。v0.2 每本完成即 save_manifest,重跑自动跳过 ocr:true 的记录。

## 检索层设计依据(v0.2)
- 实践对照:同一套清洗流程的姊妹库,焊了检索协议+写作方法论层的被高频使用,只有"grep 检索"一句话的闲置。素材是地基,检索层才是杠杆,所以 build 固定产出 SOIL.md(协议)+CATALOG.md(粗筛层)。
- 两级检索的物理载体:CATALOG.md 每文件一行(标题|类目|字数|关键词|摘要|路径),grep 它=粗筛;命中按路径深读=精读。避免 agent 全库通读烧上下文。
- tags/excerpt 是零成本词频法+首段截取,糙但够粗筛;真摘要留给会话内子 agent 按需做,只做高价值类目。
- query.py 加权:标题×5 / 标签摘要×3 / 正文×1(封顶10),多关键词取并。空结果输出"没有命中+建议",配合 SOIL 的诚实条款。
- build 的 --index-extra:INDEX.md 是生成物,手工维护的索引区块(如精细结构化目录)必须走这个参数拼接,否则重建即丢。
